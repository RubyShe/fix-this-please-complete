<pr_title>
Fix PageFile concurrent read/write race: replace SemaphoreSlim with ReaderWriterLockSlim
</pr_title>

<pr_description>
After the multi-file storage refactoring, `PageFile` had a data race between `ReadPage()` (no lock) and the resize path in `WritePage()` (held `SemaphoreSlim`). When `WritePage()` grew the file it called `_mappedFile.Dispose()` then reassigned `_mappedFile`; a concurrent `ReadPage()` could hit `CreateViewAccessor()` on the disposed instance → `ObjectDisposedException`. The non-volatile `_mappedFile` field also lacked a memory barrier on the reader side.

## Changes

### `PageFile` locking model (`PageFile.cs`)

- **Replace** `SemaphoreSlim _lock` with `ReaderWriterLockSlim _rwLock` (`NoRecursion`) for all synchronous page I/O
- **Add** `SemaphoreSlim _asyncLock` for `FlushAsync` / `BackupAsync` — these must hold a lock across `await` and cannot use `ReaderWriterLockSlim`
- **Read lock**: `ReadPage()` and non-growing `WritePage()` — shared, allows full read/write concurrency on distinct pages
- **Write lock**: `Open()`, `AllocatePage()`, `FreePage()`, resize path of `WritePage()`, `Flush()`, `Dispose()` — exclusive, safe to replace `_mappedFile`
- **Extract** `ReadPageCore` / `WritePageCore` / `EnsureCapacityCore` as lock-free private helpers; `AllocatePage` and `FreePage` call these directly since they already hold the write lock, avoiding recursive acquisition
- **`Dispose()`** acquires `_asyncLock` before `_rwLock` — establishes a consistent lock ordering to prevent deadlock against in-flight async ops

```csharp
// Before: ReadPage had no lock at all
public void ReadPage(uint pageId, Span<byte> destination)
{
    using var accessor = _mappedFile.CreateViewAccessor(...); // ← races with WritePage resize
    ...
}

// After: shared read lock keeps _mappedFile stable across the call
public void ReadPage(uint pageId, Span<byte> destination)
{
    _rwLock.EnterReadLock();
    try   { ReadPageCore(pageId, destination); }
    finally { _rwLock.ExitReadLock(); }
}
```

### Tests (`MultiFileStorageTests.cs`)

Four new async concurrent tests: `ConcurrentReadWrite_MainFile_NoCrash`, `ConcurrentReadWrite_IndexFile_NoCrash`, `ConcurrentReadWrite_CollectionFile_NoCrash`, and `ConcurrentAllocateAndRead_NoCrash` — the last one specifically targets the `AllocatePage` file-growth write lock racing against active `ReadPage` read locks.
