### How It Works

1. **Automatic Monitoring**: Every 30 seconds, the Celery beat scheduler triggers `check_all_custom_actions_health()` which queues individual health checks for all custom actions that have a health endpoint configured.

2. **Health Check Logic**: Each check makes an HTTP GET request to the configured endpoint with a 5-second timeout. If the response status code is in the 2xx range, the status is set to "up". Any other response or error sets it to "down".

3. **Visual Feedback**: The status is displayed in the Custom Actions table with color-coded DaisyUI badges. Users can click the refresh button next to any status to trigger an immediate check.

4. **User Experience**: When a user clicks "Check Now", the button shows a loading spinner while the health check task runs. The page updates seamlessly via HTMX without requiring a full page reload.

### Technical Description

Custom action servers sometimes go down, but failures only surface when users review execution traces. This PR adds automatic health monitoring with visual status indicators.

**Implementation:**

- **Database**: Three fields on `CustomAction`: `health_endpoint` (optional URL), `health_status` (enum: unknown/up/down), `last_health_check` (timestamp)

- **Automated checks**: Celery task runs every 30 seconds, makes GET requests with 5s timeout to configured health endpoints. 2xx responses = up, everything else = down.

- **UI**: Status column in table with DaisyUI badges (green/red/gray). HTMX-powered "Check Now" button for immediate checks. Shows loading spinner during requests.

- **Security**: Team-scoped with permission checks, uses existing URL validation patterns.

Example usage:
```python
action = CustomAction.objects.create(
    name="Payment API",
    server_url="https://api.payment.com",
    health_endpoint="https://api.payment.com/health",  # Optional
    ...
)
# Status automatically updated every 30s
# Users see green/red badge in table
```
