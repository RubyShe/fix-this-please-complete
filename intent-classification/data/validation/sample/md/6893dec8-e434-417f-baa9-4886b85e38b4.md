<pr_title>
Fix regex source generator emitting invalid code for lazy loops inside lookarounds
</pr_title>

<pr_description>
## Description

Fixes a code generation bug where the regex source generator would emit invalid C# code for patterns containing lazy loops inside lookbehinds/lookaheads followed by additional content, such as `(?<=(abc)+?123)a`.

The generated code would fail to compile with errors like:
```
error CS0159: No such label 'LazyLoopBacktrack' within the scope of the goto statement
```

## Root Cause

Lookarounds (lookbehinds and lookaheads) are implicitly atomic constructs that should prevent any backtracking state from leaking out to subsequent code. However, the code generator had a subtle bug:

When a lookaround's child was marked as "atomic-by-ancestor" during analysis (which happens because the child inherits the atomic property from its lookaround parent), the lookaround would call `EmitNode` instead of `EmitAtomic`. The `EmitAtomic` path properly saves and restores the `doneLabel` (which tracks where to jump on match failure), isolating backtracking state from subsequent code. Without this isolation, backtracking labels set by lazy loops inside the lookaround would leak out and cause subsequent code to attempt invalid jumps.

## Changes

### RegexGenerator.Emitter.cs
- **`EmitPositiveLookaroundAssertion`**: Now always calls `EmitAtomic` to ensure proper isolation of backtracking state, regardless of whether the child may backtrack
- **`EmitNegativeLookaroundAssertion`**: Same change applied for negative lookarounds
- **`EmitAtomic`**: Updated assertion to allow lookarounds even when their child doesn't backtrack, since lookarounds need atomic isolation for correctness

### Regex.Match.Tests.cs
- Added test cases for patterns with lazy loops inside lookbehinds:
  - `(?<=(abc)+?123)a`
  - `(?<=(abc)+?)a`
- These test cases are guarded for non-backtracking engine and will be tested across all backtracking regex engines (Interpreter, Compiled, and SourceGenerated)

## Testing

- All 3391 Match tests pass across all regex engines
- New test cases validate that the problematic patterns now compile and execute correctly
- CodeQL security analysis shows no issues

Fixes dotnet/runtime#120882
