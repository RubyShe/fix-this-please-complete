## Summary

When the watchdog sends `/clear` to refresh a hermit's context mid-session (post-close-clear or context-size-clear), a scheduled task could re-invoke `session-start` from scratch, which re-sent the "Hermit online" channel ping even though the session was never actually stopped. This was confirmed via a live operator log showing the exact re-invocation path.

The fix is a consume-on-read boolean in `state/runtime.json`: the watchdog writes `context_cleared: true` before sending `/clear`, and session-start step 3 detects and consumes it (sets to `false`) before deciding whether to send the step-8 startup ping.

Closes #385

## Changes

- **`hermit-watchdog.ts`**: Both clear paths (`maybePostCloseClear`, `maybeContextClear`) write `context_cleared: true` via `writeRuntimeJson` inside the lifecycle lock, before the `sendKeys('/clear')` call — ensuring the marker is durable before session-start can race the watchdog.
- **`skills/session-start/SKILL.md`**: Step 3 gains a "Context-refresh detection" sub-bullet as its first action: reads `context_cleared`, sets local `suppress_startup_ping = true` if the marker is set, then unconditionally writes `context_cleared: false` (consumes on every path including fast-path and recovery branches that stop early). Step 8 adds `suppress_startup_ping` as an additional skip condition.
- **`agents/session-mgr.md`**: `context_cleared` registered in the field-ownership table as a dual-writer field with consume-on-read semantics documented.
- **`tests/watchdog.test.ts`**: `writeFakeTmux` extended with an optional `runtimeSnapshotPath` param; the bash stub snapshots `runtime.json` at the moment it receives a `/clear` send-keys. Both happy-path clear tests assert `context_cleared: true` in the snapshot, proving write-before-send (not just write-before-exit).
