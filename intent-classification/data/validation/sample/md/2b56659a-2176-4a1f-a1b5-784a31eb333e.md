The fix is complete. Here's a summary of what was changed:

## Summary

**Problem:** `wp site list --path=/support/` didn't work for filtering sites by their URL path because WP-CLI's global `--path` parameter (which sets the WordPress installation directory) intercepts it before it reaches the command.

**Solution:** 

1. **`src/Site_Command.php`**:
   - Removed `path` from the generic `$site_cols` array that auto-maps `--<field>` parameters to DB columns — since `--path` is always consumed by WP-CLI globally, it was effectively dead code there.
   - Added explicit handling for a new `--site-path=<path>` parameter that maps to the `path` DB column, avoiding the naming conflict entirely.
   - Updated the docblock to document `--site-path` and explain why `--path` can't be used directly.

2. **`features/site.feature`**:
   - Added a Behat test to verify `wp site list --site-path=/first/` correctly filters the site list by path.

**Usage:**
```bash
# Filter sites by path
wp site list --site-path=/support/

# This still doesn't work (global --path intercepted), but is now documented:
# wp site list --path=/support/
```

## Changes

- **`src/Site_Command.php`**: Removes `path` from the generic `$site_cols` auto-mapping loop (it was unreachable) and adds explicit handling for `--site-path=<path>`, which maps to the `path` column in `wp_blogs`.

- **`features/site.feature`**: Adds a Behat scenario asserting `--site-path` correctly filters results.

## Usage

```bash
# Before: silently ignored or used as WP install path
wp site list --path=/support/

# After: works as expected
wp site list --site-path=/support/
```
