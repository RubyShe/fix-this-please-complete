&gt; ### Description
&gt; 
&gt; After the 8.7 → 8.8 migration, the Tasklist V2 UI's "Candidate group" filter no longer returns any tasks when a user selects one of their groups from the dropdown, even though tasks with that candidate group exist and are visible to them.
&gt; 
&gt; The Tasklist V2 UI dropdown is populated from currentUser.groups (via GET `/v2/authentication/me`), which after 8.8 returns Group IDs (e.g. `front_support_retail_ch`). The selected value is then passed as filter.candidateGroup to POST `/v2/user-tasks/search`, where it is matched as an exact string against the indexed candidateGroups field of the task. That field contains whatever was modelled in the BPMN, which per Camunda's own documentation in 8.7 — was the Group Name (e.g. Front Support Retail CH). The two no longer match, so the filter returns zero results.
&gt; 
&gt; This is the V2 counterpart of the V1 regression already fixed by @koevskinikola in camunda/camunda#38515. That fix translated groupIds → groupNames server-side in the Tasklist V1 controller before evaluating user-task access. The same translation has not been applied to the V2 search path.
&gt; 
&gt; ### Steps to reproduce
&gt; 
&gt; 1. Create an 8.7 cluster.
&gt; 2. In Identity, create a user group, e.g. Front Support Retail CH, and assign a user to it.
&gt; 3. In the Web Modeler, create a process with a user task whose candidateGroups = Front Support Retail CH.
&gt; 4. Deploy and start an instance of the process.
&gt; 5. Verify in Tasklist V1 that the user from the group can see the task.
&gt; 6. Upgrade the cluster to 8.8 (or, equivalently, on a fresh 8.8 cluster create a Group where the name and ID differ — e.g. name Front Support Retail CH, id front_support_retail_ch).
&gt; 7. Open Tasklist V2 as the group member.
&gt; 8. In the "Filter tasks" panel, open the "Candidate group" dropdown and select the group (the dropdown shows front_support_retail_ch).
&gt; 9. Apply the filter.
&gt; 
&gt; 
&gt; ### Current behavior
&gt; 
&gt; 1. The Candidate group dropdown displays the Group ID (front_support_retail_ch).
&gt; 2. Applying the filter results in an empty task list.
&gt; 3. The underlying call POST `/v2/user-tasks/search` with `filter.candidateGroup = "front_support_retail_ch" `returns 0 results.
&gt; 4. Calling the same endpoint directly with `filter.candidateGroup = "Front Support Retail CH"` (the original Group Name as written in the BPMN) returns the tasks correctly.
&gt; 
&gt; ### Expected behavior
&gt; 
&gt; When a user selects one of their groups in the Tasklist V2 candidate-group filter, the resulting search should return all user tasks whose BPMN candidateGroups reference that group — regardless of whether the modeller used the Group Name or the Group ID.
&gt; 
&gt; ### Workaround
&gt; 
&gt; Either:
&gt; 
&gt; - Call POST `/v2/user-tasks/search` directly, passing the original Group Name (as written in the BPMN) as the candidateGroup filter value, or
&gt; - Update all BPMN process definitions to reference the new Group ID instead of the Group Name in candidateGroups.
&gt; 
&gt; Neither is a reasonable ask of customers with existing process definitions in production
&gt; 
&gt; 
&gt; ### Environment
&gt; 
&gt; SaaS &amp; SM
&gt; 
&gt; ### Version
&gt; 
&gt; Tasklist - 8.8
&gt; 
&gt; 
&gt; ### Rootcause
&gt; 
&gt; This is the same class of regression as camunda/camunda#38515, but on the V2 search path:
&gt; 
&gt; - Identity in 8.7: Groups were defined only by Group Names; the name was the unique identifier.
&gt; - Identity in 8.8: Groups are defined by both groupId (immutable, unique) and name (display label). The 8.7 → 8.8 migration sets groupName = `<existing name>` and groupId = `<slugified name>`.
&gt; - Tasklist V2 UI: The candidate-group dropdown in `FieldsModal.tsx` is sourced from `currentUser.groups`, which (after 8.8) returns Group IDs via the new `CamundaAuthentication` layer.
&gt; - Tasklist V2 search API: UserTaskFilterTransformer builds an exact-match term query against the `CANDIDATE_GROUPS` field of the task index. That field contains whatever the BPMN modeller wrote, which per Camunda's pre-8.8 docs — is the Group Name.
&gt; - Net effect: the UI sends an ID, the index holds a name, the strings don't match, the filter returns nothing.
&gt; 
&gt; The V1 fix in camunda/camunda#38515 added `TaskController.resolveGroupNames(...)`, which uses `GroupServices` to translate the authenticated user's `groupIds` back to `groupNames` before querying. The V2 path needs an equivalent translation step.
&gt; 
&gt; ### Solution ideas
&gt; 
&gt; A couple of possible directions, in rough order of preference:
&gt; 
&gt; - Resolve group IDs → group names at the V2 search layer. When the V2 search receives` filter.candidateGroup = <id>`, look up the corresponding Group Name via` io.camunda.service.GroupServices` and rewrite the filter to match against the name (or both, as an $in over [id, name]). This mirrors V1 fix in camunda/camunda#38515.
&gt; 
&gt; - Make `UserTaskFilterTransformer` accept either form. Translate the incoming candidateGroup value into an $in filter containing both the Group ID and the resolved Group Name, so that BPMN process definitions referencing either form continue to work. This is robust to mixed customer data (some BPMNs may already use IDs, others still use names).
&gt; 
&gt; - In the Tasklist V2 candidate-group dropdown, display the Group Name to the user but keep the Group ID as the value being passed to the API, once the backend can resolve either form. This avoids the UI also confusing the user, who today sees the slug instead of the human-readable name they modelled with.
