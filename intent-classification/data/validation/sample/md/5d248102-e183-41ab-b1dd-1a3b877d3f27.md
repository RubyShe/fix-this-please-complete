- Uses named constant `SUBMENU_MIN_WIDTH` (200px) matching CSS

**CSS Changes** (`packages/block-library/src/navigation/style.scss`):
- Restructured so default behavior is downward opening (no class required)
- Added `.submenu-opens-on-horizontal-hover` class that enables horizontal opening on medium+ breakpoints
- Works for both navigation blocks with and without backgrounds
- When class is absent, naturally reverts to downward opening

## Summary

I successfully addressed @scruffian's performance optimization feedback for the navigation submenu overflow fix.

### Changes Made (commit 65744cf)

**Optimized the overflow detection logic:**

Previously, the code would:
1. Add the `submenu-opens-on-horizontal-hover` class
2. Measure if submenu would overflow
3. Remove the class if overflow detected

This resulted in an unnecessary add-then-remove pattern when overflow would occur.

**New optimized approach:**
1. Measure submenu width first (without adding the class)
2. Check if it would overflow
3. **Only add** the class if submenu will fit
4. **Only remove** the class if it would overflow AND the class is already present

### Benefits

- **Better performance**: Avoids unnecessary DOM manipulations
- **Cleaner logic**: Check condition first, then act accordingly
- **Same functionality**: Maintains exact same behavior while being more efficient
- **Fewer reflows**: Only manipulates the DOM when actually needed

### Code Structure

The refactored logic now follows a more intuitive pattern:
```javascript
// Measure first
const submenuWidth = withMeasurementStyles(...);
const wouldOverflow = parentRect.right + submenuWidth > window.innerWidth;

// Then conditionally manage class
if (wouldOverflow) {
    if (hasClass) remove();
} else {
    if (!hasClass) add();
}
```

This is more performant than the previous "add first, then maybe remove" approach, especially in cases where the submenu would overflow, as it now avoids the unnecessary class addition.
