- If successful, it resumes the embedded flow by loading the returned request:

**Takeaway**
This is a canonical example of the “**delegate/navigation-action orchestration**” pattern:
- the webview boundary detects a special condition
- it cancels navigation
- it runs custom logic (network/crypto/challenge)
- it resumes by loading a new request back into the same embedded webview session

## What this implies for Mobile Onboarding (your two requirements)

### Requirement A: special redirect URLs (`msauth://enroll`, `msauth://compliance`, `msauth://enrollment_complete`)
These behave much closer to **PKeyAuth** than switch-browser:

- They are **mid-flight navigations** that instruct the client to do work (BRT acquisition once per redirect) and then load a constructed next URL with required params/headers.
- That is exactly “cancel/replace navigation with a new request” behavior.

So the best-fitting implementation model is the **navigation-time interception pattern** (PKeyAuth-like).

### Requirement B: response headers for telemetry + header-driven ASWebAuth handoff
This is also webview-boundary logic:
- headers are available at navigation-response time
- the decision “launch ASWebAuth now” must happen at that moment

You *can* model the actual “launch ASWebAuth” part using the **switch-browser style response/operation** *internally*, but the *trigger point* still naturally lives at the navigation delegate boundary.

## What this means for Mobile Onboarding: my recommendation (now grounded in these patterns)

### My recommendation remains:
**Use the PKeyAuth-style navigation-time interception (delegate pattern) as the primary orchestration for Mobile Onboarding.**

### Why (in repo terms)
- `msauth://enroll` and `msauth://compliance` behave like **PKeyAuth**: they are **mid-flight navigation instructions** that require:
  - intercept/cancel,
  - do BRT acquisition (once per redirect),
  - construct the real next URL from query params + add required query params/headers,
  - and then load the request.
- The header-driven ASWebAuth trigger is also most naturally decided at the **navigation-response boundary**, because that’s where headers exist.

### Where to reuse the switch-browser idea
Even if the *trigger* is delegate/navigation-time, you can still reuse the **switch-browser encapsulation** idea for the actual “launch system web auth and convert callback URL into a response,” because that’s a proven, testable unit in this repo.

So the clean boundary is:

- **Delegate/navigation-time owns detection + decision** (special redirect URLs, response headers, telemetry decisions).
- **Operation/response object can own execution of ASWebAuth launch** (optional reuse), returning a callback URL that the controller feeds back into the normal flow.

## Updated recommendation (final)
Use **delegate / navigation-time orchestration (Approach A)** as the primary architecture for Mobile Onboarding, because it naturally supports **cancel/replace navigation** and **resuming the same `WKWebView` instance** after doing off-webview work (BRT acquisition, header-driven ASWebAuth handoff).

### Why the “resume same embedded session” requirement is decisive
Resuming the same embedded session implies you must preserve:
- the **same `WKWebView` instance lifecycle** (navigation state, back/forward list)
- cookies/session continuity as observed by that webview (or at least keep the same webview container and continuation semantics)
- an uninterrupted “in-progress” web auth session (you’re not completing and restarting auth; you’re continuing it)

This is exactly how the repo’s **PKeyAuth** pattern works:
- intercept in navigation delegate
- `decisionHandler(WKNavigationActionPolicyCancel)`
- run handler
- then `loadRequest:` back into the **same webview**

Trying to force this through “completeAuth → factory response → controller operation” increases the risk that you accidentally model the event as a terminal outcome and lose “same webview continuation” semantics.

### Best-practice boundary (to avoid dual-path complexity)
- **Delegate path owns detection + stateful continuation**:
  - `msauth://enroll`, `msauth://compliance`: cancel navigation → BRT acquisition once per redirect → build final URL with required headers/query params → load in same webview
  - response headers: telemetry + detect ASWebAuth handoff → temporarily suspend webview UI → launch ASWebAuth → on callback load callback URL into same webview
- **Response objects** only represent *semantic end states* (e.g., `msauth://enrollment_complete`, final success/error), not “continue-the-flow” redirects.

If you still want to reuse the switch-browser modularity, you can encapsulate *only* “launch ASWebAuth and return callback URL” as a helper/operation, but the orchestration and resumption should remain in the embedded-controller delegate so it always returns to the same `WKWebView`.
